# 部署与运营

本项目提供一个单机生产部署：Caddy 自动申请并续期 HTTPS 证书，Node 应用与后台各自运行，PostgreSQL 不暴露宿主端口，数据库持久化，每天生成备份。适合初期小规模运营；尚不提供多机高可用、托管运维或支付结算。

## 一条命令部署

准备一台 Ubuntu 22.04 / 24.04 或 Debian 12 / 13 服务器，建议至少 2 核、2 GB 内存、20 GB 可用磁盘。把自己的域名 A / AAAA 记录指向该服务器，安全组和防火墙放通 TCP 80、443。不要给没有 IPv6 连通能力的服务器添加 AAAA 记录。

以 root 登录服务器，把下面的域名、支持邮箱和 SMTP 值换为你自己的真实值后，执行这一条命令。SMTP 服务商的授权密码可先通过 `read -rs SMTP_PASS; export SMTP_PASS` 输入，避免把密码放进 shell 历史。

```sh
curl -fsSL https://raw.githubusercontent.com/1075375006/liang-ge-ren/main/ops/install.sh | DOMAIN='app.你的域名.com' SUPPORT_EMAIL='支持邮箱@你的域名.com' SMTP_HOST='你的SMTP主机' SMTP_PORT=587 SMTP_SECURE=false SMTP_USER='你的SMTP账号' SMTP_FROM='你的发信邮箱' bash
```

如已用环境变量提供 `SMTP_PASS`，管道右侧的安装程序会继承该变量。SMTP 465 端口通常使用 `SMTP_SECURE=true`；587 通常为 `false`。是否需要 `SMTP_USER/SMTP_PASS` 取决于服务商。SMTP_FROM 可以是 `两个人 <hello@your-domain.com>`。

这条命令从公开源码仓库下载安装入口，在缺少 Docker 时使用 Docker 官方 apt 软件源安装 Engine 与 Compose 插件，克隆到 `/opt/liang-ge-ren`，部署当前 `main`。可以通过 `INSTALL_DIR=/自定义绝对路径` 修改目录，通过 `REF=完整提交SHA` 固定到已审阅的提交。已有安装目录必须是本项目的干净 Git 仓库，否则停止并保留已有文件。

其他 Linux 系统先安装 Docker Engine、Compose v2、Git、OpenSSL 和 curl，再克隆项目，运行：

```sh
DOMAIN='app.你的域名.com' SUPPORT_EMAIL='支持邮箱@你的域名.com' SMTP_HOST='你的SMTP主机' SMTP_FROM='你的发信邮箱' bash scripts/deploy.sh
```

首次执行必须提供真实域名、支持邮箱、SMTP 主机与发件人；脚本不会猜测这些值。没有这些外部资源时不能完成公开运营部署。部署程序不替你购买域名、设置 DNS、申请邮件服务或完成服务器所在地要求的备案。

## 脚本做了什么

1. 校验生产配置；生成 64 位十六进制随机数据库密码，写入 `.local/production/production.env`，目录权限 700、配置权限 600。后续执行使用原配置，不自动覆盖密钥、域名或用户数据。若配置丢失但已存在数据库卷，立即停止并要求恢复原配置，不尝试用新密码接管数据。
2. 按 Git 提交 SHA 构建应用镜像，每次构建使用唯一镜像标签，记录镜像 ID、数据库备份与版本。同一提交重新构建也不会覆盖旧镜像标签；未提交源码会带 `dirty` 标记。构建失败不停止现有服务。
3. 确认数据库健康，停止前台和后台写入，备份数据库，再执行版本化迁移。应用、后台心跳、积分对账、SMTP 连接/TLS/认证校验和 `/api/ready` 全部通过后开放 Caddy。SMTP 校验不发送邮件。
4. 等待真实域名的 HTTPS `/api/ready` 返回成功且版本与本次构建一致，防止 DNS 指向其他旧实例时误报成功；失败时返回非零状态，并保留数据库、原镜像、升级前配置和备份。升级出错会保持应用停止，避免带故障继续接收写入，不会擅自覆盖数据库回退。
5. 启动每日数据库备份，自动备份保留至少 14 天。手动备份与升级前备份不会被自动清理。

数据库首次启动会记录实际 PostgreSQL 镜像摘要 `POSTGRES_IMAGE`；已有数据库以当前容器的实际镜像为准固定摘要，并使用 `--no-recreate`。普通应用更新不拉取新的 PostgreSQL 版本，后续服务启动也不重建数据库。PostgreSQL 升级应安排独立维护窗口，先备份并在副本验证兼容性；不能通过普通应用更新悄悄跟随滚动标签升级。

生产环境默认启用注册邮箱验证。SMTP 配置校验通过并不等于真实邮件一定送达；首次开放推广前，应实际注册两个账号，确认验证邮件和找回密码邮件能够进入收件箱，完成配对、约定验收及心愿兑换。域名发信还需要邮件服务商要求的 SPF、DKIM、DMARC 设置。

生产默认 `SMTP_REQUIRE_TLS=true`，587 端口必须能升级到 STARTTLS；465 使用 `SMTP_SECURE=true`。只有你明确使用可信私网的明文邮件中继时，才将 `SMTP_REQUIRE_TLS=false`；本地 Docker 验收对隔离的 Mailpit 使用此设置。

`OPERATOR_NAME` 可以填写真实运营主体名称；不填写时产品使用通用名称，不会伪造公司信息。`SUPPORT_EMAIL` 是用户支持和隐私请求联系地址。`ACME_EMAIL` 默认使用支持邮箱，可另行设置证书提醒邮箱。

## 配置与版本

生产部署使用 `ops/compose.production.yaml`，不要与根目录供本地体验使用的 `compose.yaml` 混用。所有下列操作都在安装目录执行。

```sh
cd /opt/liang-ge-ren
bash scripts/status.sh
```

状态检查包含容器状态、积分对账、后台心跳、最近自动备份与真实 HTTPS 就绪检查。生产 Compose 不映射数据库或应用端口，只开放 Caddy 的 80/443。应用容器以非 root 用户运行、根文件系统只读、去除 Linux capabilities，并限制日志滚动大小。

配置保存在 `.local/production/production.env`。修改 SMTP、运营联系方式、微信凭据或注册开关时直接编辑该文件，然后重新运行部署。shell 中新设置的同名变量不会覆盖已有生产配置。`REGISTRATION_OPEN=false` 可临时关闭新注册，已有账号仍可使用。不要手工更改已经初始化数据库的 `POSTGRES_PASSWORD`；它不是数据库密码轮换操作。

查看日志：

```sh
docker compose --env-file .local/production/production.env -f ops/compose.production.yaml logs --tail=100 app worker caddy backup
```

查看发布记录：

```sh
cat .local/production/releases.log
```

配置、备份、日志都在 Git 和 Docker 构建上下文之外。保管该配置文件并另存一份受保护的副本；其中包含数据库和邮件凭据。不要把 `docker compose config` 的完整输出发布到公开渠道。

## 更新

推荐重新执行上面的单行安装命令：它会获取最新 `main` 并调用部署脚本，使用已有配置，无需重新填 SMTP 密钥。或者使用指定提交：

```sh
curl -fsSL https://raw.githubusercontent.com/1075375006/liang-ge-ren/main/ops/install.sh | REF='要部署的完整提交SHA' bash
```

若从自己的 Git 工作区维护，先取得并审阅新代码，再运行 `bash scripts/deploy.sh`。升级时有短暂维护窗口。脚本使用目录锁防止多个部署、手工备份与恢复同时运行；进程异常被强制终止后，仅在确认没有这些操作运行时，才能删除 `.local/production/operation.lock` 空目录。

## 备份与恢复

手动备份：

```sh
bash scripts/backup.sh
```

会输出一个 `*.dump` 文件路径，旁边有 SHA256 校验文件；脚本还会校验 PostgreSQL 归档目录。每日自动备份使用同一目录 `.local/production/backups`，以 `auto-` 开头；失败后每 5 分钟重试，超过 26 小时未成功则容器健康状态变为异常。自动备份仅在新的备份成功后清理过期自动文件。

数据库卷解决容器重启后的持久化，不能防止整台服务器丢失。至少每天把备份、配套 `.sha256` 和生产配置复制到另一台机器或加密对象存储，并定期在独立实例恢复演练。当前项目会报告备份健康状态，但尚未配置任何外部告警接收方，需用你的监控平台监测 HTTPS `/api/ready` 和 `scripts/status.sh`。

恢复指定备份会覆盖当前应用数据库，因此命令要求明确参数，并在执行前再次备份当前库：

```sh
bash scripts/restore.sh /绝对路径/manual-时间.dump --confirm-replace-database
```

恢复先验证备份与 SHA256，再停止入口、应用、后台和自动备份，备份停止写入后的当前数据库，重建应用 schema，导入归档并执行当前版本迁移。先用一次性应用容器完成积分对账，通过后才启动应用、后台和自动备份，待 `/api/ready` 通过后再打开 Caddy。任何恢复步骤失败都会显式停止业务服务，保留数据库与恢复前备份。不要对非本项目数据库运行此命令。

升级失败需要回退整个版本时，先读取升级错误中打印的旧镜像、`previous.env` 和升级前备份路径。确认没有需要保留的新版本写入后，恢复上一份配置，再恢复对应备份：

```sh
cp .local/production/previous.env .local/production/production.env
bash scripts/restore.sh /升级错误中给出的/before-deploy-时间.dump --confirm-replace-database
bash scripts/status.sh
```

`previous.env` 仅代表最近一次尝试前的配置，`last-success.env` 代表最近一次成功部署配置；需要回退更久版本时，使用发布记录和你保留的配置。初次部署失败不存在可回退的旧应用。镜像不会自动清理，确认不再需要回退后再由运维按保留策略清理。日常停机不要执行 `docker compose down -v`，该参数会删除持久数据库卷。

## 验证边界

本次在开发机使用独立 Docker 项目验证构建、数据库初始化、容器健康、备份与恢复；具体结果记录在项目验收记录。真实服务器、真实 DNS 的 ACME 证书申请、真实 SMTP 投递与微信平台需要目标环境的外部配置，未在开发机伪称上线验证。生产部署脚本会在目标服务器进行实际 HTTPS 与后台就绪检查。

可重复运行 `bash ops/test-deploy.sh` 检查部署安全分支，运行 `bash ops/test-production.sh` 验证真实容器、本地 CA HTTPS、本地 SMTP、两个账号的验证与配对、密码重置和备份恢复。前者使用模拟 Docker，后者强制使用随机项目名、隔离配置和随机本机端口，忽略 shell 中的生产项目名、数据库、SMTP 和备份目录覆盖。测试结束核对实际资源的项目标签后，才移除测试容器及专属卷；测试文件保留在被 Git 忽略的 `.local/ops-tests/` 或 `.local/lgr-smoke-*`，便于审计。`bash ops/test-production.sh --config-only` 仅解析配置，不启动或删除任何 Docker 资源。
